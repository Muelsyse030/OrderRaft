## 3. 剩余提示级问题

### 3.1 `IdempotencyConflicts` 计数只能从测试触达

**位置**:`internal/fsm/fsm.go:80-85`(导出方法)、`:151-173`(累加与日志)

该计数是线程安全的导出方法,但服务器二进制中**没有任何调用方**(`grep` 确认仅测试使用),也没有指标端点暴露。实际可观测性完全依赖 `slog.Warn` 日志。

**建议**:二选一——保持现状并把方法注释改为"供测试与嵌入式使用,进程本身通过 warn 日志暴露";或把它接进 gRPC(`GetOrderResponse` 不可行,宜另加一个简单状态 RPC/`grpc_health` 之外的诊断端点)。当前注释"该计数是节点本地可观测指标"略带误导性,因为它并不真正可观测。

### 3.2 FSM 使用 `slog`,进程其余部分使用标准 `log`

**位置**:`cmd/main.go:41-43`(`slog` handler 指向 `output`)与其他位置的 `log.Printf`

两条日志流格式、级别过滤策略不同,输出到同一 writer 时会交错,`-log-level` 只影响 slog 侧。功能无碍,但运维阅读体验割裂。

**建议**:统一到 `slog`(把 `log.Printf` 换成注入的 `logger.Info`),或在 README 的日志说明里点明两者并存。

### 3.3 恢复期回放失败虽已留痕,但仍是"跳过该条"

`Apply` 现在会记录解码失败,但该条已提交日志仍被跳过,节点状态与多数派静默偏离;`ErrApplyFailed` 只在用户触发路径上外显。

**建议**:这属于"到什么程度算可接受"的策略选择。若要更进一步,可在连续解码失败时主动 `raft.Shutdown()` 或暴露健康状态为不健康(让编排系统重启并用持久化快照重建),而不是带着偏离的状态继续服务。当前项目无持久化存储,重启即可重建,因此现状可接受——建议在 README「已知限制」中点明这一取舍。

### 3.4 低优先级:FSM 日志字段可更完整

`recordIdempotencyConflict` 只带 `request_id`;`logError` 只带 `index`/`term`/`error`。增加 `order_id`、`user_id` 等字段会让生产排障更直接。

## 4. 本轮未发现的问题(明确说明)

我针对以下历史上容易出错的点做了定向检查,均**未发现问题**:

- `Apply` 在所有分支都返回 `*ApplyResponse`(`runFSM` 的类型断言不会 panic),包括新增的非 `LogCommand` 分支;
- 快照字节所有权转移后无别名共享(探测验证),`Release()` 置 nil 不影响已持久化内容;
- `forceStopGrace` 有界等待不会让关闭流程被永不返回的 handler 拖死;
- 幂等语义三条路径(校验失败 / 状态相关失败 / 成功决策)与注释描述完全一致,探测逐一验证;
- 生成代码与 proto 定义一致(第三轮已用真实 `protoc` 验证,本轮无 proto 改动)。
